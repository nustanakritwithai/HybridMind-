## 1. Mission and non-goals

**Main Agent thinks. Typhoon Worker builds exactly one widget. Deterministic backend validates and renders. User authorizes consequential actions.**

Deliver a recognizable visual/interactive learning experience through reusable widgets—not text-heavy articles with decorative blocks. Content is still accessible as text and references.

V0.1 DOES NOT:
- grant Typhoon planning, publishing, user administration, shopping, email or transaction privileges;
- let Typhoon edit adjacent widgets, browse WordPress administrator content, call arbitrary tools or connect externally;
- assume the existing Typhoon Chat v0.2.2 endpoint is a Widget Worker API;
- promise safe execution of arbitrary AI-authored JavaScript in production;
- change published reference Post #55 or launch the site.

## 3. Trust boundaries and architecture

\`\`\`mermaid
flowchart LR
  U[User] --> M[ChatGPT Main Agent / Editorial Planner]
  M -->|One signed WidgetRequest| API[Authenticated Widget Request API]
  API --> V1[Request Authorization & Input Validator]
  V1 -->|Restricted facts/type/slot| T[Typhoon Widget Worker]
  T -->|Declarative WidgetCandidate JSON| V2[Output Validator & Fact/Policy Gate]
  V2 -->|PASS| L[Versioned Widget Library]
  L --> R[Trusted Renderer + Local State Engine]
  R --> P[Isolated Preview]
  P --> Q[QA / Human Approval]
  Q -->|Approved and authorized| W[Draft-only WordPress Slot Writer]
  W --> D[WordPress DRAFT]
  V1 -->|FAIL| E[Reject and report reason]
  V2 -->|FAIL| E
\`\`\`

Trust Zone A: Main Agent drafts article storyline and exact per-widget scope. **No direct widget HTML/JS injection.**

Trust Zone B: WordPress backend authenticates/authorizes requests and holds the Typhoon key server-side. Backend enforces the immutable scope before the model is called and again after output.

Trust Zone C: Typhoon receives only relevant **public or explicitly approved inputs** and outputs a structured candidate for **one** widget. It cannot decide to publish, enlarge article scope, select backend tools or add secret-bearing URLs.

Trust Zone D: Renderer is trusted application code. It binds strict schema data to pre-reviewed components; controls local interaction and isolates each widget by \`widget_id\`/version. Never execute returned model-authored code in this lane.

Trust Zone E: Separate experimental code sandbox, **future phase only**, may compile/render user-approved new widget code on a dedicated isolated origin with audited CSP and no privileged bridges. It is not part of the safe V0.1 acceptance path.

No \`html\`, \`css\`, \`javascript\`, \`onclick\`, plugin hook, WP credentials or remote URL is accepted from Typhoon in the safe V0.1 lane. If a new visual cannot be composed from supported primitives, return \`UNSUPPORTED_WIDGET_TYPE\` or propose a new type for **separate architectural review**.

### 4.3 Error contract

\`{ request_id, widget_id, status: "REJECTED", error: { code, message, retryable } }\`

Stable validation codes to design: \`BAD_SCHEMA\`, \`MISSING_INPUT\`, \`UNSUPPORTED_WIDGET_TYPE\`, \`OUT_OF_SCOPE\`, \`NOT_A_DRAFT\`, \`STALE_VERSION\`, \`UNVERIFIED_SOURCE\`, \`MODEL_TIMEOUT\`, \`UNSAFE_OUTPUT\`, \`QA_FAILED\`, \`COST_LIMIT\`.

A failed widget must not create or modify a second widget. On retry, the same idempotency key and expected revision must not result in duplicates.

## 5. Widget Library and deterministic renderer

### V0.1 reusable widget families

\`hero-story\`, \`concept-diagram\`, \`comparison-cards\`, \`glossary-grid\`, \`interactive-architecture-map\`, \`scenario-comparison\`, \`example-prompt-lab\`, \`quiz\`, \`step-sequence\`, \`insight-quote\`, \`do-dont\`, \`source-list\`.

Some inventory rows are parts of a larger widget; for example a 3-tab map should be **one widget with internal tabs**, not three worker requests. Use common design tokens and built-in locally controlled interactions.

Renderer API concept: \`render(widget_spec, widget_version, theme_tokens) -> safe DOM\`.

Renderer invariants:
- allowlist component types / properties, fixed depth and bounded list lengths;
- render model-supplied strings with \`textContent\`, not \`innerHTML\`;
- all CSS scoped by \`widget_id\`, no body/global selectors in widget output;
- internal state and event handlers are authored in reviewed renderer code;
- default **no external network access** and no side-effect actions;
- accessible labels, focus order, keyboard activation, source links, alt descriptions;
- mobile 320/375/390/768/1280px and reduced-motion test grid.

Storage draft design: WordPress custom post type or custom table (\`hm_visual_widget\`, each record keyed by article/draft + widget_id + version), plus immutable JSON candidate, validated render version, source IDs, input digest, QA report. Do not assume the existing Typhoon Chat plugin already implements these types.

## 6. Widget Event Bridge

Allowed V0.1 events from a widget to trusted parent:

- \`widget.ready\`, \`widget.resize\` (bounded pixel dimensions/rate);
- \`widget.select\` (whitelisted local state and value);
- \`widget.quiz_answer\` (local answer index; no personal data);
- \`widget.copy_result\` (local copy feedback only).

Other event types are rejected. **A click is not a permission to run an AI agent, invoke WordPress tools, make a payment, send email, or call external APIs.**

Each message must carry protocol version, widget_id, monotonically increasing event ID, validated payload shape and a per-render capability token (not an API key). Parent validates sender \`source\` against the registered iframe and checks per-widget capability; for sandboxed opaque origins, origin may be \`null\`, so **origin string alone is insufficient**. Only bounded resize/scroll results are acted upon. Throttle resize events and prevent recursive layout loops.

**Strong preference:** For trusted declarative widgets, render directly using the known host component library—no iframe required. Reserve sandboxed iframes for verified third-party or future generated-code scenarios.

## 7. Sandboxing policy

The current published lesson's iframe is sandboxed without \`allow-same-origin\`, but includes \`allow-popups allow-popups-to-escape-sandbox\`. For AI-generated widgets, do **not** copy that permissive configuration.

**V0.1 safe lane:** no AI-authored code runs. Only validated data is passed to trusted renderer components.

**Experimental generated-code lane (future, not Production):**
- Load in a dedicated isolated origin / separate hosted sandbox, not a privileged WordPress administrator origin.
- Start with \`sandbox="allow-scripts"\`, do NOT add \`allow-same-origin\`, \`allow-popups\`, \`allow-popups-to-escape-sandbox\`, top-level navigation, form submission or downloads.
- Apply **enforced HTTP CSP** on the isolated widget serving origin (not merely a report-only policy), e.g. \`default-src 'none'; connect-src 'none'; form-action 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'\`; selectively allow only hashed/verified static JS/CSS assets if needed. Correct CSP rules must be tested against the actual serving origin and use case.
- Static scan and semantic capability allowlist, runtime memory/time limits in backend if any execution occurs there, request quota, strict event bridge and emergency kill-switch.
- Explicit approval before experimental code is embedded in Production; if any requirement cannot be enforced, return \`UNSAFE_OUTPUT\` rather than using raw Gutenberg HTML.

## 8. Backend and Typhoon integration (design only)

Suggested WordPress-side plugin (not installed): **Hybrid Mind Visualize Engine** with authenticated REST routes such as:

- \`POST /wp-json/hm-visual/v1/requests\` — create one version-checked scoped widget request.
- \`GET /wp-json/hm-visual/v1/requests/{id}\` — task status (authorized users only).
- \`GET /wp-json/hm-visual/v1/previews/{id}\` — noindex, authenticated preview.
- \`POST /wp-json/hm-visual/v1/widgets/{id}/approve\` — explicit owner/editor approval.
- \`POST /wp-json/hm-visual/v1/widgets/{id}/apply-to-draft\` — modify exactly one draft-bound slot, not Published posts.

**These routes are proposals only.** They do not exist on the current WordPress installation.

Typhoon adapter should call its API **server-side** under a separate narrowly constrained prompt with a fixed JSON output contract. Do not reuse the visitor-facing \`/hybridmind/v1/chat\` endpoint as if it were a trusted Worker API. Audit how the current plugin stores credentials, then use an approved server-side adapter without returning the key, and test provider output for schema compliance. **Typhoon's ability to consistently emit valid widget JSON in Production is UNKNOWN** until tested.

The caller (Main Agent) may receive the generated candidate or validate status, but may **not** write directly into the page without backend validation and approval.

## 9. Release states and gates

\`REQUESTED → AUTHORIZED → GENERATED → VALIDATED → PREVIEW_READY → QA_PASS → APPROVED → APPLIED_TO_DRAFT\`

\`PUBLISHED\` belongs to a **separate editorial release process** not controlled by the Widget Worker. Widget generation alone is not publication.

Every state transition records actor, timestamp, request_id, widget_id, expected version, input/output digest, allowed sources and result. Invalid transitions return an error; no silent fallback.

One request can create/replace only one declared widget in a WordPress **Draft**; the WordPress Post #55 published lesson remains read-only during development.

| # | Limitation / evidence | Severity | Resolution | Acceptance gate |
| --- | --- | --- | --- | --- |

| L02 | Existing plugin is chat/knowledge only; no Widget Request API | P0 | Design separate authenticated WordPress plugin + worker adapter | Confirm route and permission behavior on staging, NEVER assume chat endpoint |
| L03 | Typhoon may output arbitrary text/code or hallucinate widgets | P0 | Strict JSON Schema, whitelist of component types, no raw HTML/JS | Invalid or out-of-scope output rejected with stable code |
| L04 | Prompt cannot guarantee scope isolation | P0 | Backend immutable target, \`expected_widget_version\`, idempotency and source checks | Cross-widget modification attempts **0 accepted** in negative tests |
| L05 | Future generated scripts may access services or exfiltrate data | P0 | No model JS in V0.1; separate experimental isolated origin + CSP later | Network/exfiltration test denied; no credentials to widgets |
| L06 | Current bridge uses wildcard messaging and one iframe | P0 | Per-widget source/capability/event allowlist and size caps | Spoofed/incorrect-source event ignored, never edits WP |
| L07 | Template \`innerHTML\` safe only because data is static today | P0 | Safe DOM text rendering; all inputs treated as untrusted | XSS fixtures rendered inert |
| L08 | Content images/data may be inaccurate or unlicensed | P0 | Source/claim ledger, asset rights and alt text requirements | All factual modules trace to approved source refs |
| L09 | New freeform visual shapes cannot be safely accepted by current renderer | P1 | Combine reusable primitives first; separate sandbox research for new code | New unsupported types return explicit error |
| L10 | UI may overflow or break on real Android/browser | P1 | Responsive token system and real device/viewport matrix | 320/375/390/768/1280 screenshots, keyboard, focus, no horizontal overflow |
| L11 | Browser privacy/network rights and model costs can expand | P1 | Hard quotas, per-user rate, payload/time limits; approved model/config | Budget limit reached → safe rejection, no additional tasks |
| L12 | WordPress draft rendering and revision rollback not yet proven | P1 | Draft-only idempotent slot writer, revision snapshots, readback & rollback | One-slot edit leaves other slots and Published #55 unchanged |
| L13 | WordPress coming-soon prevents anonymous production visual QA | P1 | Signed-in browser/staging QA; DO NOT open site to test | Authenticated QA evidence exists before release |
| L14 | “A2A” currently describes conceptual delegation, not deployed A2A protocol | P2 | Start with versioned JSON envelopes, add optional Agent2Agent transport adapter later | Do not advertise Agent2Agent compliance without protocol tests |
| L15 | Existing dynamic UX (copy/quiz/tab) has isolated local state assumptions | P1 | Trust-owned state machines with unique per-widget scope | Two same-type widgets operate independently |
| L16 | Many widget formats can degrade performance | P1 | Lazy initialize below-fold widgets, bounded assets, per-article widget budget | Perf & accessibility budget measured on staging, no regressions |
| L17 | Agent output could silently mutate Published content | P0 | Authorize only Draft target; human editorial release gate separate | Publish endpoint unauthorized from Worker and widget controls |

**Prioritize L01–L08 and L17 before any new Dynamic Widget Generation.** Risks are not closed by better prompting.
