# แผนระยะที่ 1 สำหรับสารบัญความรู้ HybridMind


**ขอบเขต:** ออกแบบและเตรียมหนังสือความรู้แบบอ่านเป็นหัวข้อทีละบท พร้อมสารบัญและการค้นพบเนื้อหา ระยะที่ 1 ยังไม่พัฒนาแชต Open Typhoon และยังไม่เปลี่ยนหรือเผยแพร่เนื้อหาบนเว็บไซต์

## สรุปและข้อเสนอ

HybridMind ควรเพิ่มหนังสือความรู้แบบโต้ตอบและมีภาพประกอบ ที่ทำให้บทความมากกว่า 200 บทความในปัจจุบัน และคลังที่อาจเติบโตเกิน 1,000 บทความในอนาคต เรียนรู้ต่อและดูแลได้ง่ายขึ้น ผู้อ่านเลือกหัวข้อหนึ่ง อ่านให้จบ แล้วไปหัวข้อถัดไปที่มีชื่อชัดเจนได้ โดยคง WordPress เป็นแหล่งเนื้อหาหลักและรักษา URL เดิมไว้ สารบัญจะจัดระเบียบแนวคิดและเส้นทางการเรียนรู้ ส่วนข้อความ บล็อก Gutenberg ภาพ ตาราง และสื่อโต้ตอบที่มีอยู่ยังอยู่ในบทความต้นทาง ไม่คัดลอกมาเขียนซ้ำหรือสร้างภาพตกแต่งปลอมเพื่อเติมทุกหัวข้อ

ระยะนี้ส่งมอบแบบจำลองข้อมูลและสารบัญหลัก ข้อกำหนดการค้นหาและการเชื่อมข้อมูลกับ WordPress ต้นแบบประสบการณ์ค้นพบ แผนย้ายข้อมูลและทดสอบ ตลอดจนเกณฑ์เปิดใช้งานที่ตรวจสอบได้ การเลือกผู้ให้บริการค้นหาหรือกราฟความรู้ยังรอผลทดสอบคำค้นภาษาไทยและการเปรียบเทียบทางเทคนิค แผนนี้เป็นข้อเสนอ ไม่ใช่รายงานว่าระบบใดถูกติดตั้งหรือใช้งานแล้ว

## เป้าหมายและขอบเขต

### ผลที่ต้องการ

- ผู้อ่านเริ่มจากคำถาม ปัญหา ระดับความรู้ หรือเป้าหมาย แล้วไปถึงบทความที่เหมาะได้โดยไม่ต้องรู้ชื่อบทความล่วงหน้า
- เห็นความเชื่อมโยงระหว่างแนวคิด บทความ และเส้นทางเรียนรู้อย่างมีเหตุผล พร้อมรู้ว่าควรอ่านอะไรก่อนหรือหลัง
- ค้นภาษาไทยได้ดี รวมคำพ้อง คำย่อ คำอังกฤษที่ใช้ปนภาษาไทย และคำถามแบบภาษาธรรมชาติ
- ทีมบรรณาธิการจัดหมวดและปรับโครงสร้างได้ โดยไม่เปลี่ยน URL หรือทำให้บทความซ้ำ
- ข้อมูลพร้อมส่งออกให้ระบบค้นหาและ RAG ในอนาคตได้ โดยนำเข้าเฉพาะเนื้อหาที่เผยแพร่แล้วและผ่านเงื่อนไขสิทธิ์
- รองรับจำนวนบทความที่เพิ่มขึ้นโดยไม่ต้องสร้างสารบัญใหม่ทุกครั้งหรือพึ่งพาการจัดหมวดด้วยมือเพียงอย่างเดียว

### อยู่ในระยะที่ 1

- ตรวจสอบรายการบทความ หมวดหมู่ URL และโครงสร้างหัวข้อปัจจุบัน
- ออกแบบสารบัญหลัก บท/หัวข้อย่อย คำถามที่ผู้อ่านใช้ค้นหา และเส้นทางการเรียนรู้
- กำหนดรหัสเนื้อหาถาวร เมทาดาทาแบบมีความหมาย และความสัมพันธ์ระหว่างหัวข้อ
- วางแบบ API และกระบวนการซิงก์ที่ทำซ้ำได้อย่างปลอดภัยจาก WordPress
- ออกแบบหน้าสำหรับค้นหา สำรวจตัวกรอง ดูหน้าแนวคิด และเลือกอ่านต่อ
- ให้หน้าอ่านหัวข้อเป็นประสบการณ์หลัก มีปุ่มบทก่อนหน้า/บทถัดไปพร้อมชื่อหัวข้อ และมีสถานะความคืบหน้าบนอุปกรณ์นี้เมื่อผู้อ่านเลือกเปิดใช้
- สร้างชุดทดสอบคำค้นภาษาไทย เกณฑ์คุณภาพ และประตูตัดสินใจก่อนเลือกเทคโนโลยีค้นหา
- ในการเปรียบเทียบเทคโนโลยี ให้เริ่มมองตัวเลือก AI-native ที่พัฒนาอย่างต่อเนื่อง รวมการค้นแบบผสม การค้นเชิงความหมาย และ reranker ไว้ในสิ่งที่ต้องประเมิน แต่ยังไม่เลือกเครื่องมือจนกว่าจะผ่าน benchmark และตรวจทรัพยากร deploy/ดูแลจริง
- วางแผนความปลอดภัย การควบคุมสิทธิ์ การสำรองข้อมูล การย้อนกลับ และการตรวจสอบหลังเผยแพร่

### อยู่นอกระยะที่ 1

- แชต Open Typhoon หรือแชตที่ตอบจากคลังบทความ ซึ่งเป็นขอบเขตของระยะที่ 2
- สร้างบทความใหม่ ย้ายเนื้อหา เปลี่ยน Gutenberg หรือแก้ URL จริง
- สร้างกราฟความรู้ขนาดใหญ่หรือแยกสำเนาบทความเป็นฐานข้อมูลเนื้อหาใหม่
- ฟีดสังคม ระบบติดตามผู้เขียน ไลก์ คอมเมนต์ หรือเกมมิฟิเคชัน
- เลือกผู้ให้บริการค้นหาหรือคลังเวกเตอร์ก่อนผ่านการทดสอบภาษาไทยและการทบทวนข้อเสนอทางเทคนิค

## ภาพรวมระบบและข้อเท็จจริงที่ใช้วางแผน

1. WordPress ยังคงเป็นแหล่งจริงของบทความ สื่อ สถานะเผยแพร่ และ URL เดิม สารบัญและดัชนีค้นหาเป็นชั้นข้อมูลที่สร้างต่อจากแหล่งจริงและสร้างใหม่ได้
2. มีบทความมากกว่า 200 ชิ้นและมีแนวโน้มเติบโตถึง 1,000 ชิ้นขึ้นไป ตัวเลขนี้ใช้กำหนดความสามารถในการขยายระบบ ไม่ใช่จำนวนที่ตรวจนับใหม่ในแผนนี้
3. ปัจจุบันมีหมวด WordPress 8 หมวด แต่หมวดเหล่านั้นทับซ้อนกัน จึงไม่ควรถือว่าเป็น 8 หัวข้อเฉพาะหรือ 8 บทของสารบัญโดยอัตโนมัติ ต้องทำคลังรายการและจับกลุ่มตามเจตนาเนื้อหาก่อน
4. มีแนวคิดสคีมาภาพที่กล่าวถึงรหัส article, module, source และ claim แล้ว แต่ยังไม่มี anchor ของหัวข้อบทความตามข้อมูลที่ได้รับ ควรตรวจของจริงและทำให้รหัสหัวข้อคงที่ก่อนใช้งานกับสารบัญ
5. เอกสารประวัติของ Typhoon ระบุการตั้งค่า v0.2.2 ณ วันที่ 9 ตุลาคม 2026 แต่สถานะปัจจุบันยังไม่ได้ยืนยัน และยังไม่มีซอร์สปลั๊กอินสาธารณะที่ตรวจสอบได้ในข้อมูลที่มี แผนนี้จึงไม่ถือว่าการเชื่อมต่อดังกล่าวพร้อมใช้งาน
6. ไม่ได้ยืนยันว่ามีส่วนใดของแผนนี้ถูกนำไปติดตั้งหรือเผยแพร่แล้ว

## โครงสร้างสารบัญหลักที่เสนอ

หัวข้อด้านล่างเป็นร่างสำหรับตรวจสอบกับบทความจริง ไม่ใช่การยืนยันว่าเว็บไซต์มีบทเหล่านี้อยู่แล้ว บทความหนึ่งอาจปรากฏในหลายเส้นทางหรือเชื่อมกับหลายหัวข้อได้ โดยไม่ต้องทำสำเนา

### 0. เริ่มเรียนตามเป้าหมาย

- เพิ่งเริ่มใช้ AI: ต้องรู้แนวคิดอะไร และควรทดลองอย่างไร
- ต้องการตรวจคำตอบ AI: ตรวจข้อเท็จจริง ตัวเลข แหล่งอ้างอิง และข้อจำกัดอย่างไร
- ต้องการสร้างผู้ช่วยตอบจากเอกสาร: เตรียมข้อมูล ค้นคืน และอ้างอิงอย่างไร
- ต้องการให้เอเจนต์ใช้เครื่องมือ: กำหนดขอบเขต สิทธิ์ และจุดอนุมัติอย่างไร
- ต้องการนำระบบขึ้นใช้งาน: ทดสอบ เฝ้าดู และรับมือเมื่อผิดพลาดอย่างไร

### 1. พื้นฐาน AI และโมเดลภาษา

- AI, machine learning, generative AI และโมเดลภาษาต่างกันอย่างไร
- โมเดลสร้างข้อความจากอะไร และเหตุใดจึงตอบผิดได้
- บริบท โทเคน หน้าต่างบริบท และข้อจำกัดความรู้หมายถึงอะไร
- โมเดลเปิด โมเดลปิด การรันในเครื่อง และบริการ API มีข้อแลกเปลี่ยนอย่างไร
- ควรใช้ภาษาไทยหรือภาษาอังกฤษกับโมเดลเมื่อใด

### 2. การสั่งงานและการออกแบบผลลัพธ์

- คำสั่งที่ชัดเจนควรระบุเป้าหมาย บริบท ข้อจำกัด และรูปแบบผลลัพธ์อย่างไร
- จะยกตัวอย่างให้โมเดลทำตามโดยไม่ทำให้โจทย์กำกวมได้อย่างไร
- จะบังคับรูปแบบ JSON ตาราง หรือรายการตรวจสอบได้อย่างไร
- ควรถามต่อหรือแบ่งงานยาวออกเป็นขั้นอย่างไร
- จะออกแบบคำสั่งให้ตรวจสอบที่มาและระบุความไม่แน่ใจอย่างไร

### 3. ความรู้ การค้นหา และ RAG

- RAG คืออะไร และต่างจากการฝึกโมเดลหรือการวางข้อความใน prompt อย่างไร
- ควรแบ่งเอกสารเป็นชิ้นอย่างไรโดยไม่ตัดใจความหรือแหล่งอ้างอิง
- การค้นคำสำคัญ การค้นความหมาย และการค้นแบบผสมต่างกันอย่างไร
- จะรักษารุ่นเอกสาร แฮช แหล่งที่มา และตำแหน่งข้อความอ้างอิงอย่างไร
- จะตรวจสิทธิ์ของผู้ใช้ก่อนโหลดเอกสารเข้าสู่ระบบค้นคืนอย่างไร
- จะลดคำตอบที่ไม่มีหลักฐานหรืออ้างอิงไม่ตรงกับข้อความต้นฉบับอย่างไร

### 4. เอเจนต์และการใช้เครื่องมือ

- เอเจนต์ต่างจากแชตบอตแบบตอบครั้งเดียวอย่างไร
- ควรให้เอเจนต์เรียกเครื่องมือเมื่อใด และห้ามทำอะไรบ้าง
- จะส่งงานหลายขั้นโดยมีขอบเขตและบันทึกการตัดสินใจได้อย่างไร
- การอนุมัติของมนุษย์ควรผูกกับการกระทำและข้อมูลชุดใด
- จะป้องกันการสั่งซ้ำ ความล้มเหลวบางส่วน และผลข้างเคียงจากเครื่องมืออย่างไร

### 5. การตรวจสอบ คุณภาพ ความปลอดภัย และความน่าเชื่อถือ

- จะตรวจข้อเท็จจริง ตัวเลข และคำอ้างอิงในคำตอบ AI อย่างไร
- จะทดสอบโค้ดที่ AI สร้างด้วย unit test, integration test และการทบทวนอย่างไร
- จะทำชุดทดสอบและประเมินความแม่นยำตามงานจริงอย่างไร
- Prompt injection คืออะไร และควรถือข้อความที่ดึงจากเว็บหรือเอกสารเป็นข้อมูลอย่างไร
- จะป้องกันข้อมูลรั่ว การใช้สิทธิ์เกินจำเป็น และการตอบจากเอกสารที่ผู้ใช้ไม่มีสิทธิ์อย่างไร
- จะวัดอัตราคำตอบถูก อ้างอิงได้ ปฏิเสธได้เหมาะสม และไม่ตอบเมื่อไม่มีหลักฐานอย่างไร

### 6. การสร้างระบบและการนำไปใช้งาน

- จะเชื่อม WordPress กับ API หรือระบบค้นหาโดยไม่ทำเนื้อหาซ้ำอย่างไร
- จะทำดัชนีใหม่ ซิงก์เฉพาะส่วนที่เปลี่ยน และย้อนกลับรุ่นก่อนหน้าอย่างไร
- จะติดตามเวลาแฝง ข้อผิดพลาด ค่าใช้จ่าย และปริมาณการใช้งานอย่างไร
- จะออกแบบ API และข้อมูลให้เปลี่ยนเวอร์ชันได้โดยไม่ทำลูกค้าเดิมพังอย่างไร
- จะจัดการการเผยแพร่ แก้ไข ยกเลิกเผยแพร่ และย้าย URL อย่างไร

### 7. การกำกับดูแลและกรณีใช้งาน

- จะเลือกกรณีใช้ AI ที่แก้ปัญหาได้จริงและวัดผลได้อย่างไร
- ข้อมูลใดไม่ควรป้อนให้โมเดลหรือส่งออกไปยังผู้ให้บริการ
- ใครเป็นผู้รับผิดชอบเนื้อหา การตรวจสอบ และการแก้ไขหลังเผยแพร่
- จะจัดทำบันทึกการเปลี่ยนแปลงและประกาศข้อจำกัดของระบบอย่างไร
- มีบทเรียนหรือรูปแบบการทำงานใดที่ทีมสามารถนำไปทำซ้ำได้

### คำถามนำทางที่ควรใช้เป็นภาษาของผู้อ่าน

คำถามเหล่านี้เป็นตัวอย่างของหัวข้อค้นหาและป้ายกำกับเจตนา ไม่จำเป็นต้องเป็นบทความใหม่ทั้งหมด

- “ทำอย่างไรให้ AI อ้างอิงข้อมูลจริง ไม่แต่งตัวเลขขึ้นมา?”
- “จะรู้ได้อย่างไรว่า citation ชี้ไปยังเอกสารรุ่นล่าสุด?”
- “ต้องเช็กสิทธิ์ก่อนโหลดเอกสารเข้า RAG ตรงไหน?”
- “ถ้า AI เขียนโค้ดให้ จะทดสอบอะไรบ้างก่อนใช้จริง?”
- “เอเจนต์ต้องขออนุมัติเมื่อใด และอนุมัติคำขอเดิมซ้ำได้หรือไม่?”
- “เริ่มสร้างผู้ช่วยตอบจากเอกสารภาษาไทยอย่างไร?”

## เส้นทางการเรียนรู้ที่เสนอ

เส้นทางเป็นการเรียงลำดับบทความที่มีอยู่ ไม่ใช่การคัดลอกเนื้อหา แต่ละเส้นทางควรบอกผู้เรียนว่าเหมาะกับใคร ต้องรู้อะไรก่อน ใช้เวลาประมาณเท่าไร และเมื่อจบแล้วทำอะไรได้

1. **เริ่มต้นกับ AI อย่างมีวิจารณญาณ:** พื้นฐานโมเดล → การเขียนคำสั่ง → การตรวจข้อเท็จจริง → การตรวจแหล่งอ้างอิง
2. **ตรวจคำตอบและโค้ดที่ AI สร้าง:** ข้อเท็จจริงและตัวเลข → อ้างอิง → ทดสอบโค้ด → ข้อจำกัดและการทบทวนโดยมนุษย์
3. **สร้างระบบ RAG ที่อ้างอิงได้:** เตรียมเอกสาร → แบ่งเนื้อหาและค้นคืน → ตรวจสิทธิ์ก่อนโหลด → ควบคุมแหล่งและรุ่นอ้างอิง → ทดสอบคุณภาพ
4. **สร้างเอเจนต์ที่ทำงานอย่างปลอดภัย:** ออกแบบงานและเครื่องมือ → กำหนดสิทธิ์ → ผูกการอนุมัติกับการกระทำ → ทดสอบข้อผิดพลาดและการสั่งซ้ำ
5. **ดูแลคลังความรู้ที่เปลี่ยนแปลงตลอดเวลา:** โครงสร้างเนื้อหา → ID และเมทาดาทา → ซิงก์การเผยแพร่ → วัดการค้นหา → ตรวจรอบปรับปรุง

ลำดับจริงของแต่ละเส้นทางต้องยืนยันหลังสำรวจบทความครบถ้วน และแสดงเฉพาะขั้นที่มีบทความรองรับแล้ว ขั้นที่ยังไม่มีเนื้อหาให้ระบุว่าเป็นช่องว่างบรรณาธิการ ไม่สร้างหน้าว่างที่ทำให้เข้าใจว่ามีบทความพร้อม

## การแยกบทความ หัวข้อ และส่วนย่อย

- **บทความ** คือเนื้อหาหลักใน WordPress มี URL แบบ canonical ของตนเอง รหัสบทความถาวร และสถานะเผยแพร่ของตนเอง
- **หัวข้อสารบัญ (topic)** คือหน่วยการเรียนรู้ที่มีเป้าหมายและจุดจบชัดเจน ใช้จัดบทความหรือส่วนต่าง ๆ ให้อยู่ในบริบทเดียวกัน มีรหัสถาวรและสถานะความคืบหน้าของตนเอง ไม่ใช่รหัสบทความและไม่จำเป็นต้องมี URL แยก
- **ส่วนย่อย** คือหัวข้อ H2/H3 ภายในบทความ ใช้ลิงก์ตรงไปยัง anchor เช่น `#ตรวจสอบแหล่งอ้างอิง` เมื่อส่วนนั้นมีสาระชัดเจนและช่วยผู้อ่าน ไม่ควรทำทุกย่อหน้าให้กลายเป็นรายการสารบัญ
- **เส้นทางการเรียนรู้** คือชุดบทความและหัวข้อที่บรรณาธิการเรียงตามลำดับเพื่อบรรลุเป้าหมายหนึ่งเรื่อง
- **รหัสถาวร:** ใช้ UUID หรือรหัสที่ระบบออกให้ครั้งเดียวสำหรับ `article_id`, `topic_id`, `path_id` และ `section_id` อย่าสร้างจากชื่อ ลำดับบท หรือตำแหน่งที่อาจเปลี่ยนภายหลัง การสลับลำดับหรือย้ายหัวข้อจึงไม่ทำให้ความคืบหน้าหาย
- **anchor:** กำหนดรหัสคงที่ให้หัวข้อ H2/H3 ที่เลือก เช่น `citation-current-revision`; anchor ต้องไม่ขึ้นกับเลขลำดับหรืออันดับของหัวข้อ การแก้ชื่อหรือย้ายตำแหน่งไม่ควรเปลี่ยน anchor หากจำเป็นต้องเปลี่ยน ให้เก็บ alias หรือจุดเปลี่ยนเส้นทางจาก anchor เดิม
- **revision:** แยก `article_revision` ซึ่งเปลี่ยนเมื่อบทความแก้ไข ออกจาก `topic_revision` ซึ่งเพิ่มเมื่อเปลี่ยนเป้าหมายการเรียนรู้หรือสาระสำคัญของหัวข้อ การแก้คำหรือรูปแบบเล็กน้อยของบทความไม่ควรลบสถานะอ่านจบ แต่ถ้าเป้าหมายหรือเนื้อหาหลักของ topic เปลี่ยน ให้แสดงป้าย “มีเนื้อหาสำคัญอัปเดต” และชวนอ่านทบทวน โดยเก็บประวัติความคืบหน้าเดิมไว้
- **URL เดิม:** คง URL บทความที่มีอยู่ การเปลี่ยน slug ทำได้เฉพาะเมื่อมีเหตุผลและผ่านบรรณาธิการ พร้อม redirect และตรวจลิงก์ขาเข้า ไม่เปลี่ยน URL อัตโนมัติเพราะย้ายหมวด

## แผนผังความสัมพันธ์แบบเบา

ใช้ความสัมพันธ์ที่มีชนิดชัดเจนจำนวนจำกัด แทนการสร้างกราฟซับซ้อนตั้งแต่ต้น แต่ละเส้นเชื่อมมีต้นทาง ปลายทาง ชนิด วันที่สร้าง ผู้ตรวจ และสถานะการทบทวน

| ชนิดความสัมพันธ์ | ความหมายและทิศทาง |
|---|---|
| `prerequisite` | ต้นทางเป็นสิ่งที่ควรรู้ก่อนปลายทาง |
| `explains` | ต้นทางช่วยอธิบายแนวคิดหรือข้อกล่าวอ้างในปลายทาง |
| `example` | ต้นทางเป็นตัวอย่างเชิงปฏิบัติของแนวคิดในปลายทาง |
| `contradicts` | เนื้อหาต้นทางขัดแย้งกับข้อกล่าวอ้างในปลายทาง ต้องแสดงบริบทและให้บรรณาธิการทบทวน |
| `supersedes` | ต้นทางเป็นฉบับหรือแนวทางใหม่ที่ใช้แทนปลายทางเก่า โดยเก็บร่องรอยของรายการเดิม |

ให้ตรวจความสัมพันธ์โดยมนุษย์ก่อนแสดงเป็นข้อเท็จจริงหรือแนะนำให้ผู้ใช้อ่านต่อ ระบบอาจเสนอความเชื่อมโยงเพื่อให้บรรณาธิการตรวจ แต่ห้ามสร้างเส้น `contradicts` หรือ `supersedes` แล้วเผยแพร่เอง เส้นทางการเรียนรู้สามารถเก็บลำดับของตนโดยตรง ไม่จำเป็นต้องเพิ่มชนิดความสัมพันธ์ทั่วไปที่ไม่มีนิยาม

การจัดการรายการคล้ายกันต้องแยกสถานะให้ชัด: “อาจซ้ำ” คือคิวตรวจสอบความซ้ำ ยังไม่ใช่คำสั่งลบหรือรวม; “เกี่ยวข้อง” คือคนละบทความที่ช่วยกันตอบโจทย์; “ปรับปรุง/แทนที่” ใช้ `supersedes` พร้อมเก็บบทความเก่าและ URL; “ขัดแย้ง” ใช้ `contradicts` เมื่อมีหลักฐานและคำอธิบายให้ตรวจสอบ ระบบอาจใส่รายการใน `similarity_group_id` เพื่อช่วยค้นรายการที่ควรดู แต่ห้ามรวม ลบ หรือเปลี่ยนสถานะเอง

## บทความตัวอย่างเรื่องการตรวจสอบ AI และการรักษาเจตนา

รายการเหล่านี้ควรถูกจัดเป็นคนละหัวข้อย่อยตามเจตนาการค้นหา แม้อยู่ในบทใหญ่เดียวกัน ห้ามรวมเป็นบทความเดียวเพียงเพราะทั้งหมดเกี่ยวกับความน่าเชื่อถือหรือ RAG

- การตรวจข้อเท็จจริง ตัวเลข และ citation ในคำตอบ AI: [บทความตรวจคำตอบ AI](https://hybridmind.online/2026/10/13/verify-ai-answers-facts-numbers-citations/)
- การทดสอบโค้ดที่ AI สร้าง: [บทความทดสอบโค้ด AI](https://hybridmind.online/verify-ai-generated-code-tests-thai/)
- การพิสูจน์แหล่งอ้างอิงกับรุ่นเอกสารปัจจุบัน แฮช SHA-256 และตำแหน่งไบต์ UTF-8: [บทความ RAG citation gate](https://hybridmind.online/2026/10/16/rag-citation-gate-current-revision-sha256-utf8-byte-span/)
- การตรวจสิทธิ์ก่อนนำเอกสารเข้าสู่ขั้นโหลดข้อมูล: [บทความ authorization before hydration](https://hybridmind.online/rag-document-authorization-before-hydration/)
- การผูกการอนุมัติเอเจนต์กับ action fingerprint: [บทความ agent approval gate](https://hybridmind.online/2026/10/18/agent-approval-gate-action-fingerprint/)

จัดรายการเหล่านี้ไว้ในหัวข้อที่เหมาะและอาจปรากฏในเส้นทางเรียนรู้หลายเส้นทาง แต่ให้คง URL และความหมายแยกกัน การเชื่อมเป็น `explains`, `example` หรือ `prerequisite` ให้ทำหลังอ่านเนื้อหาจริงและผ่านการทบทวน ไม่ควรอนุมานเส้นความสัมพันธ์จากชื่อ URL เพียงอย่างเดียว

## เมทาดาทาและสคีมาที่เสนอ

เก็บข้อมูลสารบัญที่ WordPress หรือชั้นข้อมูลประกอบ โดยยึดรหัส WordPress เดิมไว้สำหรับอ้างกลับ แหล่งข้อมูล canonical ยังคงเป็นบทความ WordPress

| ระเบียน | ฟิลด์สำคัญที่เสนอ |
|---|---|
| Article | `article_id`, `article_revision`, `wp_post_id`, `canonical_url`, `title`, `summary`, `locale`, `status`, `published_at`, `modified_at`, `topic_ids`, `source_hash`, `schema_version` |
| Section | `section_id`, `article_id`, `heading_text`, `heading_level`, `anchor`, `summary`, `display_order`, `article_revision`, `schema_version` |
| Topic | `topic_id`, `topic_revision`, `parent_topic_id`, `label_th`, `label_en`, `definition`, `search_aliases`, `questions`, `audience_level`, `intent`, `status` |
| Learning path | `path_id`, `title`, `audience`, `goal`, `ordered_topic_ids`, `estimated_minutes`, `prerequisites`, `status` |
| Reading progress | `path_id`, `topic_id`, `topic_revision`, `completed_at`, `progress_schema_version`; เก็บบนอุปกรณ์ของผู้อ่านเท่านั้นเมื่อเปิดใช้ |
| Relation | `from_id`, `to_id`, `type`, `rationale`, `review_status`, `reviewer_id`, `created_at`, `updated_at` |

คำค้นแทนและป้ายกำกับควรเก็บทั้งภาษาไทย อังกฤษ คำย่อ และรูปเขียนที่ใช้จริง โดยรักษาคำต้นฉบับและระบุภาษาได้ ระดับผู้อ่านอาจใช้คำว่า “เริ่มต้น”, “มีพื้นฐาน” และ “เชิงลึก” แต่ต้องกำหนดเกณฑ์ร่วมกันก่อนติดป้าย ไม่ให้การจัดหมวดเพียงอย่างเดียวทำหน้าที่แทนคำอธิบายความยาก

แยกสิ่งที่บทความเป็นออกจากสิ่งที่บทความพูดถึง: `content_type` ใช้บอกว่าเป็นคู่มือ บทอธิบาย กรณีศึกษา หรือรายการตรวจสอบ ส่วน `topic_id` บอกหัวข้อความรู้ บทความมีหัวข้อหลักหนึ่งหัวข้อ (primary topic) และหัวข้อรองได้หลายหัวข้อ ฟิลด์ที่ควรพิจารณาเพิ่มคือ `primary_topic_id`, `content_type`, `audience_level`, `last_reviewed_at`, `content_state` (เช่น published, review-needed, superseded), `related_ids` และ `similarity_group_id` สำหรับจัดกลุ่มรายการที่ควรตรวจเท่านั้น ไม่ใช่สั่งรวมบทความอัตโนมัติ หากเก็บ `related_ids` เพื่อช่วยแสดงผล ให้สร้างจากความสัมพันธ์ที่บรรณาธิการยืนยันหรือใช้เป็นฟิลด์เพื่อความเข้ากันได้ โดยระเบียนความสัมพันธ์แบบมีชนิดเป็นแหล่งจริง

แบบข้อมูลใหม่ควรเชื่อมกับรหัส `article`, `module`, `source` และ `claim` ที่มีอยู่แล้ว แทนการสร้างรหัสชุดใหม่มาทับกัน และเพิ่มรหัส `section`/anchor ที่ยังขาดหลังตรวจสอบสคีมาจริง

`source_hash` ควรคำนวณ SHA-256 จากรูปแบบข้อมูลที่กำหนดแน่นอน เช่น เนื้อหาที่ WordPress ส่งออก พร้อม title, metadata ที่ใช้ค้นหา, สถานะ, เวอร์ชัน schema และลำดับบล็อกที่เกี่ยวข้อง โดยเข้ารหัส UTF-8 และทำ canonicalization แบบเดียวกันทุกครั้ง การเปลี่ยนค่าใดที่มีผลต่อการค้นหาหรือการอ้างอิงต้องทำให้แฮชเปลี่ยน เก็บแฮชเดิมไว้เพื่อเห็นว่าเนื้อหาใดเปลี่ยนและสร้างดัชนีซ้ำเฉพาะรายการที่จำเป็น

## ประสบการณ์หนังสือและการค้นพบ

หน้าอ่านหัวข้อเป็นประสบการณ์หลัก ส่วนหน้าสารบัญ เส้นทางเรียนรู้ และการค้นหาเป็นทางเข้าหรือเครื่องมือช่วยเลือกบทถัดไป รูปแบบควรให้ความรู้สึกเหมือนหนังสือภาพประกอบสมัยใหม่ที่อ่านบนมือถือได้ดี และค้นพบหัวข้อใหม่ได้ง่าย หน้า Topic Hub แสดงคำถามที่ตอบได้ บทความต้นทาง ระดับที่เหมาะ และทางไปยังหัวข้อก่อนหน้าหรือถัดไป การ์ดแต่ละใบควรบอกประโยชน์หรือคำถามที่ตอบ แทนการแสดงชื่ออย่างเดียว

หน้าอ่านของแต่ละ topic ใช้การอ้างถึง `article_id` และ `section_id`/anchor แล้วดึงหรือแสดงผลเนื้อหาจาก WordPress ต้นทาง ไม่สร้างสำเนา prose อีกชุดหนึ่ง หากหัวข้อเดียวใช้หลายส่วนจากหลายบทความ ให้เรียงชี้ไปยังส่วนต้นทางตามลำดับการเรียนรู้ และคงลิงก์กลับไป URL canonical ของแต่ละบทความ

องค์ประกอบที่เสนอ:

- ช่องค้นหาเดียวค้นทั่วบทความและส่วนย่อย H2/H3 ที่เลือก พร้อมหัวข้อสารบัญ คำถามนำทาง ชื่อเรื่อง คำพ้อง และ glossary; ควรค้นหาตามความเกี่ยวข้องเป็นค่าเริ่มต้นและให้ผู้ใช้งานเลือกจัดตามวันที่ได้ โดยไม่จำกัดผลให้แสดงเฉพาะบทความล่าสุด
- หน้าอ่านเฉพาะหัวข้อ แสดงชื่อบท เป้าหมายการเรียนรู้ ภาพ/อินโฟกราฟิก/สื่อโต้ตอบเมื่อมีและช่วยอธิบายจริง พร้อมเนื้อหาจากบทความ WordPress ที่เกี่ยวข้องและลิงก์อ้างอิงตรง การมีภาพไม่ใช่ข้อบังคับทุกหัวข้อ และต้องรักษาภาพหรือสื่อโต้ตอบเดิมไว้
- ปุ่ม “บทก่อนหน้า: [ชื่อหัวข้อ]” และ “บทถัดไป: [ชื่อหัวข้อ]” แสดงชื่อปลายทางก่อนกดเสมอ เมื่อจบบทมีการชวนให้ทำเครื่องหมายว่าอ่านหัวข้อนี้จบแล้ว จากนั้นจึงไปหัวข้อต่อไปได้
- ตัวกรองตามหัวข้อหลัก ระดับผู้อ่าน ภาษา รูปแบบเนื้อหา และความใหม่ โดยใช้ตัวกรองเท่าที่ช่วยตัดสินใจจริง
- หน้าแนวคิดหรือ Topic Hub ที่เชื่อมบทความและคำถามในบริบทเดียวกัน แยกป้ายหัวข้อออกจากประเภทเนื้อหาอย่างชัดเจน
- อธิบายความแตกต่างระหว่างบทความซ้ำ บทความที่เกี่ยวข้อง บทความฉบับปรับปรุง/แทนที่ และบทความที่ขัดแย้งกัน โดยสถานะและความสัมพันธ์ที่สำคัญต้องผ่านบรรณาธิการ
- เส้นทางเรียนรู้พร้อมสถานะ “เริ่มที่นี่”, ลำดับอ่าน, เวลาโดยประมาณ และความก้าวหน้าที่เลือกเก็บไว้ได้เฉพาะในอุปกรณ์
- ลิงก์แชร์ที่ชี้ตรงไปยังบทความหรือ anchor ของส่วนสำคัญ พร้อมชื่อและคำอธิบายที่เข้าใจได้เมื่อแชร์
- การนำทางที่ใช้งานด้วยแป้นพิมพ์และหน้าจอสัมผัสได้ มีสถานะโฟกัสและป้ายกำกับสำหรับโปรแกรมอ่านหน้าจอ และลด/ปิดการเคลื่อนไหวตามการตั้งค่า reduced motion ของอุปกรณ์
- รองรับหน้าเว็บเรนเดอร์จากเซิร์ฟเวอร์ (SSR) และใช้งานการค้นพบพื้นฐานได้แม้ JavaScript โหลดไม่สำเร็จ

ความคืบหน้าต้องเลือกเปิดใช้ก่อน เก็บในอุปกรณ์ของผู้อ่าน ไม่ต้องมีบัญชีหรือส่งประวัติการอ่านไปยัง analytics และมีคำสั่ง “ล้างความคืบหน้า” ที่หาเจอได้ง่าย การไม่เปิดใช้หรือการล้างความคืบหน้าต้องไม่ขวางการอ่านและปุ่มบทก่อนหน้า/ถัดไป การสลับหัวข้อหรือ reorder ไม่ลบความคืบหน้าเพราะผูกด้วย `topic_id` ไม่ใช่ลำดับ หาก `topic_revision` เปลี่ยนจากการปรับสาระสำคัญ ให้แจ้งเตือนให้อ่านทบทวนโดยไม่ลบประวัติเดิม

การเติบโตแบบสื่อสังคมในที่นี้หมายถึงการค้นพบ การแชร์ และการอ่านต่อที่ลื่นไหล ไม่ได้หมายถึงการเพิ่มฟีด การติดตามผู้ใช้ หรือการเก็บข้อมูลพฤติกรรมเกินความจำเป็นในระยะนี้

## WordPress, API และการซิงก์ข้อมูล

### หลักการเชื่อมต่อ

- อ่านบทความและสถานะจาก WordPress โดยคง Gutenberg, ภาพ และบล็อกเนื้อหาไว้ที่เดิม
- สารบัญเก็บเฉพาะข้อมูลจัดระเบียบและข้อมูลนำทางที่จำเป็น ไม่เก็บสำเนาบทความฉบับแก้ไข
- ดัชนีค้นหาเป็นข้อมูลอนุพันธ์ สร้างใหม่จาก WordPress และเมทาดาทาสารบัญได้
- ใช้ WordPress REST API เป็นจุดอ่านข้อมูลบทความ และตรวจสถานะก่อนนำเข้า; เอกสาร REST API ระบุทั้งสถานะและเนื้อหาของโพสต์ โดยค่าเริ่มต้นการค้นคืนเป็นโพสต์ที่เผยแพร่แล้ว ([อ้างอิง Posts REST API](https://developer.wordpress.org/rest-api/reference/posts/))
- กำหนด API เวอร์ชันแรก เช่น `/wp-json/hybridmind/v1/` และมี `schema_version` ในข้อมูลตอบกลับเพื่อแยกเวอร์ชัน API จากโครงสร้างข้อมูล
- ออกแบบ API สำหรับอ่านสารบัญ/หัวข้อ/บทความ และรับเหตุการณ์เผยแพร่ โดยยังไม่ระบุผู้ให้บริการหรือไลบรารีจนกว่าจะผ่านการทดสอบ
- ตรวจสิทธิ์ก่อนส่งข้อมูลทุกครั้ง และให้ API สาธารณะคืนเฉพาะฟิลด์ที่อนุมัติให้เผยแพร่

### เหตุการณ์ที่ต้องรองรับ

ซิงก์เมื่อบทความถูกเผยแพร่ แก้ไข เปลี่ยนหมวด เปลี่ยนเมทาดาทาที่ใช้ค้นหา ยกเลิกเผยแพร่ ย้ายไปถังขยะ หรือถูกลบ เหตุการณ์ควรมีรหัสเฉพาะ, `wp_post_id`, สถานะ, เวลาแก้ไข, `source_hash` และเวอร์ชันสคีมา ใช้คีย์เฉพาะร่วมกับรหัสบทความและแฮชเพื่อให้การรับเหตุการณ์ซ้ำไม่สร้างรายการซ้ำ จุดเริ่มต้นที่ควรประเมินใน WordPress คือ hook หลังบันทึกโพสต์ ซึ่งทำงานหลังบันทึกโพสต์ terms และ metadata แล้ว แต่ต้องทำต้นแบบยืนยันลำดับกับ workflow จริงและเพิ่มการจัดการสถานะ/การลบให้ครบ ([อ้างอิง `wp_after_insert_post`](https://developer.wordpress.org/reference/functions/wp_after_insert_post/))

การประมวลผลควรรับมือเหตุการณ์ซ้ำ มาช้า หรือผิดลำดับได้ มีคิว retry และ dead-letter สำหรับรายการที่ล้มเหลว พร้อมรายงานและปุ่ม replay ที่บันทึกผู้ดำเนินการ การเผยแพร่หรือแก้ไขต้องทำให้ดัชนีปรับตามแหล่งจริง การยกเลิกเผยแพร่ต้องถอนออกจากผลค้นหา ส่งออก และแหล่งข้อมูล RAG โดยเร็ว ไม่ทิ้งหน้าแคชสาธารณะที่ยังเข้าถึงได้ การลบจริงให้ใช้ tombstone หรือเครื่องหมายถอนรายการเพื่อให้ระบบปลายทางลบตาม โดยไม่ลบหลักฐานประวัติการซิงก์ทันที

### การส่งออกและความพร้อมต่อ RAG

เตรียมส่งออกเป็น JSON หรือ NDJSON ที่มีรหัส บทความ canonical URL สถานะเผยแพร่ แหล่งที่มา แฮช เวลาแก้ไข หัวข้อ anchor และเมทาดาทาที่ผ่านการอนุมัติ ไฟล์ส่งออกต้องสร้างซ้ำได้และระบุเวลาสร้างกับ `schema_version` การส่งออกในอนาคตให้รวมเฉพาะบทความที่เผยแพร่และผู้ใช้ระบบปลายทางมีสิทธิ์อ่าน ห้ามรวม draft, private, pending review, เนื้อหาที่ถอนเผยแพร่, โฆษณา, ข้อความฝังคำสั่งที่เป็น prompt injection, ข้อมูลส่วนบุคคลหรือข้อมูลลับ และส่วนที่ไม่ได้รับอนุญาต

การเตรียมข้อมูลนี้ไม่ได้เปิดใช้ RAG ในระยะที่ 1 ระยะที่ 2 ต้องบังคับใช้สิทธิ์ก่อน hydrate หรือโหลดเอกสารจริง ไม่อาศัยการซ่อนผลหลังค้นหาเป็นมาตรการสิทธิ์เพียงอย่างเดียว

## ประตูคุณภาพการค้นหาภาษาไทยก่อนเลือกเทคโนโลยี

ยังไม่เลือกผู้ให้บริการค้นหาจากการสาธิตหรือคำโฆษณา ให้สร้างชุดทดสอบภาษาไทยและทดสอบระบบที่เข้ารอบด้วยข้อมูลบทความจริงที่อนุมัติให้ใช้ก่อนการตัดสินใจ

1. สุ่มและจัดทำ benchmark ประมาณ 60–100 คำค้นที่สะท้อนโจทย์จริงจากกลุ่มเนื้อหาหลัก รวมคำถามแบบยาว คำพ้อง คำสะกดผิดเล็กน้อย คำอังกฤษผสมไทย คำย่อ การค้นหาชื่อบทความ การค้นเจาะส่วนย่อยของบทความ และคำค้นที่ควรไม่พบผล
2. ให้ผู้เชี่ยวชาญอย่างน้อยสองคนกำหนดบทความที่เกี่ยวข้องและระดับความเกี่ยวข้องโดยไม่รู้ว่าผลมาจากระบบใด แล้วทบทวนความเห็นต่าง
3. ทำ Thai bakeoff แบบเจาะจงระหว่างสองตัวเลือกที่ควรทดสอบก่อน คือ Meilisearch และ Typesense ไม่ขยายเป็นรายการเครื่องมือหกตัว ให้เริ่มพิจารณาเทคโนโลยีที่กำลังพัฒนาอย่างต่อเนื่องและมีความสามารถ AI-native สำหรับการค้นแบบ semantic/hybrid ในยุคหลัง AI ก่อน โดยไม่ตัดสินจากอายุผลิตภัณฑ์เพียงอย่างเดียว และไม่เลือกแบบ legacy-first หากยังไม่พิสูจน์ว่าตอบโจทย์กว่า
4. Meilisearch ควรทดสอบการแบ่งคำไทยที่เอกสารระบุว่ามี tokenizer แบบพจนานุกรม พร้อมการค้นแบบผสมระหว่างคำสำคัญกับความหมาย และการกำหนดภาษาให้ฟิลด์หลายภาษา ส่วน Typesense ควรทดสอบ locale `th` และกฎแบ่งคำไทย รวม full-text และ vector query ใน API ของตน เอกสารแสดงความสามารถที่ควรนำเข้าการทดสอบ แต่ไม่ใช่หลักฐานว่าระบบใดจะชนะกับคำถามจริงของ HybridMind
5. ประเมิน reranker (ขั้นจัดอันดับผลค้นใหม่) แยกเป็นความสามารถที่ต้องทดสอบใน pipeline ของแต่ละตัวเลือก ตรวจว่าต้องใช้ส่วนเสริมใดและมีค่าใช้จ่าย/เวลาแฝงเพิ่มเท่าไร อย่าสันนิษฐานว่ามีให้ในตัวจากเอกสาร hybrid/vector search
6. ทดสอบทั้งผลค้นระดับบทความและส่วนย่อย แยกชุดคำถามไว้ให้เห็นว่าการคืน snippet พร้อม anchor ช่วยการอ่านจริงหรือไม่
7. วัด Recall@5, NDCG@10, อัตราค้นไม่พบ, ความแม่นยำของตัวกรอง, เวลาแฝง P95, คุณภาพคำค้นไทย/อังกฤษผสม, ความแม่นยำระดับบทความและส่วนย่อย ตลอดจนพฤติกรรมหลังแก้ไขหรือถอนบทความ
8. เปรียบเทียบด้วยชุดเนื้อหาและชุดคำค้นเดียวกัน วัด latency, หน่วยความจำ/CPU หรือทรัพยากรที่ใช้จริง, ค่า embedding/reranker และค่าดำเนินงานต่อเดือนภายใต้โหลดเป้าหมาย
9. ทดสอบคำค้นที่มีสิทธิ์เข้าถึงต่างกันและคำที่ล่อให้ระบบส่งข้อมูล private เพื่อยืนยันว่าไม่มีข้อมูลหลุดในผลลัพธ์หรือ snippet

**เกณฑ์ตั้งต้นที่เสนอ ยังไม่ได้วัด:** Recall@5 ไม่น้อยกว่า 0.85, NDCG@10 ไม่น้อยกว่า 0.75, อัตราค้นไม่พบไม่เกิน 5% สำหรับชุดคำถามที่มีคำตอบในคลัง, ผลค้นระดับส่วนย่อยต้องชี้กลับไปยังบทความและ anchor ที่ถูกต้อง, เวลาแฝง P95 ต่ำกว่า 600 มิลลิวินาทีภายใต้โหลดทดสอบที่ตกลงกัน และไม่มีผล private/unpublished ในการทดสอบสิทธิ์ เป้าหมายเหล่านี้ต้องทบทวนหลังได้ baseline และต้นทุนจริง ไม่ควรใช้เป็นคำรับรองผลก่อนทดสอบ

ข้อเสนอทางเทคนิค ณ ตอนนี้คือทำ bakeoff สองตัวเลือก Meilisearch กับ Typesense เท่านั้น แล้วตัดสินจากคำค้นภาษาไทยจริง คุณภาพระดับบทความ/ส่วนย่อย latency ทรัพยากร ความเป็นส่วนตัว ค่าใช้จ่าย การส่งออก/สร้าง index ใหม่ และภาระ deploy/ดูแล ตัวเลือกใดไม่ผ่านให้ตัดออกโดยไม่ขยาย bakeoff ไปยังผู้ให้บริการรายอื่น เว้นแต่ผลทดสอบพบช่องว่างสำคัญที่ต้องเปิดการตัดสินใจใหม่ แนวทางที่ต้องทดสอบคือ hybrid retrieval และ reranking; อย่าเลือกจากความใหม่หรือเก่าเพียงอย่างเดียว

## ความปลอดภัย สิทธิ์ และการใช้ AI ช่วยงานบรรณาธิการ

- กำหนดบทบาทแยกผู้เขียน ผู้แก้ไขสารบัญ ผู้ตรวจทาน และผู้ดูแลระบบ ใช้สิทธิ์น้อยที่สุดและบันทึกการเปลี่ยนแปลง
- การเปลี่ยนโครงสร้างหัวข้อ ความสัมพันธ์ที่มีความเสี่ยง การเปลี่ยน anchor หรือการถอนบทความต้องเห็นผู้กระทำ เวลา และค่าก่อน/หลัง
- AI ช่วยเสนอหัวข้อ คำพ้อง สรุป หรือความเชื่อมโยงได้ แต่ทุกข้อเสนอที่ส่งผลต่อผู้อ่านต้องอยู่ในสถานะ draft และมีผู้ตรวจทาน
- ห้ามให้ agent เผยแพร่บทความหรือสารบัญอัตโนมัติ ห้าม merge draft เข้าสู่สารบัญที่เผยแพร่ และห้ามลบความสัมพันธ์หรือบทความอัตโนมัติ
- ปฏิบัติต่อข้อความในบทความ เอกสารภายนอก และผลค้นคืนเป็นข้อมูล ไม่ใช่คำสั่งให้ระบบทำงาน ดักจับหรือกักข้อความ prompt injection ก่อนส่งต่อให้ agent
- แยกสภาพแวดล้อมทดสอบกับ production เก็บ secrets ในระบบจัดการความลับ ไม่ใส่ในโค้ด log หรือไฟล์ export
- ตั้ง retention ของ log ให้พอแก้ปัญหาโดยไม่เก็บข้อมูลส่วนบุคคลเกินจำเป็น จำกัดการเข้าถึง log และ export
- ตรวจการแคชและ CDN ให้แน่ใจว่าการถอนเผยแพร่ลบข้อมูลจากหน้าเว็บ API และ snippet ภายใน SLA ที่ตกลงกัน

## การเข้าถึง ความเร็ว และการดูแลเนื้อหา

- ตั้งเป้าการเข้าถึงตาม WCAG 2.2 AA สำหรับหน้าค้นหา สารบัญ การ์ด ตัวกรอง และเส้นทางเรียนรู้ รวมถึงการขยายตัวอักษร ลำดับหัวข้อ และข้อความทดแทนภาพ
- ตรวจการใช้งานบนโทรศัพท์ก่อนเดสก์ท็อป และทดสอบหน้าจอขนาดเล็ก การเชื่อมต่อช้า และการใช้แป้นพิมพ์
- ตั้งเป้า Core Web Vitals บนมือถือที่เปอร์เซ็นไทล์ 75: LCP ≤ 2.5 วินาที, INP ≤ 200 มิลลิวินาที และ CLS ≤ 0.1 โดยต้องวัดหลังมี baseline และข้อมูลจริง
- render เนื้อหาหลักจากเซิร์ฟเวอร์ มีชื่อหน้าและ metadata ที่เข้าใจได้ เปิดใช้ URL ของบทความเดิม และทำ structured data เฉพาะที่ตรงกับเนื้อหาจริง
- ใช้ canonical URL ของ WordPress เป็นจุดอ้างอิงเดียว หลีกเลี่ยง URL พารามิเตอร์ตัวกรองจำนวนมากที่ทำให้เกิดหน้าซ้ำในผลค้นเว็บ
- ใช้ glossary ที่อธิบายศัพท์ยากด้วยภาษาคนทั่วไป มีคำไทย อังกฤษ คำย่อ และลิงก์กลับหัวข้อหลัก
- ให้บรรณาธิการกำหนดรอบตรวจทานหัวข้อและเส้นทาง และให้ระบบแจ้งเนื้อหาที่ไม่มีหัวข้อ มีลิงก์เสีย หรือใช้หมวดล้าสมัย โดยไม่แก้เอง

## การปฏิบัติการ สำรอง และย้อนกลับ

- เก็บ backup ของเมทาดาทาสารบัญ API configuration และ index snapshot ตามรอบที่กำหนด รวมถึงสำรองฐาน WordPress ตามกระบวนการเดิม
- ทดสอบการกู้คืนตัวอย่างก่อนเปิดใช้จริง ไม่ถือว่ามี backup จนกว่าจะกู้คืนและตรวจ hash ได้
- แยก release ของสคีมา สารบัญ และหน้าค้นหาเป็นขั้น พร้อม feature flag เพื่อปิดส่วนใหม่ได้โดยไม่กระทบหน้า WordPress เดิม
- ก่อน backfill เก็บ snapshot ของ mapping ID, URL, status และ hash เพื่อเทียบ diff และย้อนกลับ
- ใช้ canary กับชุดบทความหรือกลุ่มผู้ใช้จำกัดก่อนขยายเต็ม ตรวจ 404, ลิงก์ anchor, sync lag, search zero-result, error และความเร็ว
- กำหนด rollback trigger ล่วงหน้า เช่น พบข้อมูล private ในผลค้นหา, ถอนบทความไม่ทัน SLA, URL เดิมเสีย, sync backlog เกินเกณฑ์ หรืออัตรา error เกินเกณฑ์
- มี runbook สำหรับหยุดการซิงก์ ปิดฟีเจอร์ ย้อน schema/index กลับรุ่นก่อน และสร้างดัชนีจากข้อมูล WordPress ใหม่

## เกณฑ์ยอมรับเบื้องต้น

เกณฑ์ต่อไปนี้เป็นเป้าหมายที่เสนอ ไม่ใช่ผลทดสอบที่วัดแล้ว

- บทความที่เผยแพร่ทุกชิ้นในขอบเขต backfill มี `article_id`, URL canonical, สถานะ และ `source_hash`; รายการที่ไม่เผยแพร่ไม่แสดงในหน้าสาธารณะหรือ index
- การเผยแพร่ แก้ไข และถอนเผยแพร่สะท้อนในระบบปลายทางภายในเวลาที่ทีมตกลง โดยไม่มีระเบียนซ้ำเมื่อ replay เหตุการณ์เดิม
- ไม่เปลี่ยน URL บทความเดิมในงานระยะนี้ และไม่มี anchor หรือ `section_id` ของ H2/H3 ที่เลือกใช้เปลี่ยนเพราะเปลี่ยนลำดับหรือชื่อหัวข้อ
- ผู้อ่านเข้าถึงบทความจากหัวข้อหรือคำถามได้ และหน้าอ่านแสดงปุ่มบทก่อนหน้า/ถัดไปพร้อมชื่อหัวข้อปลายทาง
- หากเปิด progress ผู้อ่านเห็นสถานะความคืบหน้าตาม topic ID บนอุปกรณ์นี้เท่านั้น ไม่ต้องล็อกอิน; หากปิดหรือล้าง progress ยังอ่านได้ครบ และไม่มีการส่งประวัติอ่านไป analytics
- การแก้ไขข้อความทั่วไปไม่ทำให้สถานะอ่านจบหาย; เมื่อ topic revision เปลี่ยนเพราะสาระสำคัญ ให้เตือนทบทวนและรักษาประวัติเดิม
- ผ่านประตู benchmark ค้นหาไทย หรือระบุเหตุผลและแผนแก้ไขก่อนเลือกผู้ให้บริการ
- ไม่มีข้อมูลส่วนตัวหรือ private/unpublished ใน public API, search result, export หรือ RAG-ready set
- ผ่านการทดสอบแป้นพิมพ์ หน้าจอมือถือ และ reduced motion; สื่อโต้ตอบเดิมยังทำงาน และไม่มีข้อบกพร่องระดับรุนแรงด้านการเข้าถึง
- ผ่านเป้าหมาย performance ที่ตกลงหลังวัด baseline หรือมี exception ที่บันทึกเหตุผลและผู้อนุมัติ
- ทดสอบ rollback และ restore ได้ก่อนขยายเต็ม
- สารบัญและความสัมพันธ์ทุกส่วนที่แสดงต่อผู้อ่านมีบรรณาธิการรับผิดชอบ

## ความเสี่ยงและวิธีลดผลกระทบ

| ความเสี่ยง | ผลกระทบ | วิธีลดความเสี่ยง |
|---|---|---|
| หมวดปัจจุบันซ้อนทับ | สารบัญทำซ้ำหรือย้ายบทความไปผิดหัวข้อ | จัดทำ inventory และ mapping พร้อมเหตุผล; ไม่ยึดจำนวนหมวดเป็นจำนวนบท |
| ภาษาไทยค้นไม่ตรงความหมาย | ผู้อ่านไม่พบบทความที่มีอยู่ | สร้าง benchmark, alias และ relevance labels ก่อนเลือกเทคโนโลยี; วิเคราะห์ zero-result รายสัปดาห์หลังเปิดใช้ |
| เปลี่ยน URL หรือ anchor โดยไม่ตั้งใจ | ลิงก์เก่าเสียและสูญเสียการค้นพบ | เก็บ URL เดิม; lock anchor; ทำ redirect แบบตรวจสอบได้; รันทดสอบลิงก์ |
| เนื้อหาคัดลอกหลายที่ | ข้อมูลล้าสมัยและ citation ผิดรุ่น | WordPress เป็นแหล่งจริง; เก็บเฉพาะ metadata ที่จำเป็น; hash และสร้าง index ใหม่ได้ |
| ถอนบทความแต่ยังค้นพบจาก cache | เปิดเผยเนื้อหาที่ไม่ควรเผยแพร่ | sync unpublish ทันทีตาม SLA; purge cache/index; ตรวจ event lag และซ้อมถอน |
| ระบบ AI เสนอความสัมพันธ์ผิด | เส้นทางการเรียนรู้ชวนเข้าใจผิด | AI สร้างเฉพาะ draft; ตรวจทานทุกความสัมพันธ์; ห้าม auto-publish/merge/delete |
| vendor lock-in | ค่าใช้จ่ายหรือการย้ายระบบในอนาคตสูง | ใช้ schema ที่เป็นเจ้าของเอง, export เปิด, API version, benchmark และทดสอบ rebuild |
| หัวข้อโตเร็วกว่าเจ้าของดูแล | มีหน้าเก่า/ลิงก์เสียและโครงสร้างไม่สม่ำเสมอ | ระบุ owner ต่อบทและเส้นทาง; dashboard หัวข้อไม่มีเจ้าของ; รอบทบทวนและ runbook |

## จุดตัดสินใจที่ยังเปิดอยู่

1. เจ้าของบรรณาธิการและผู้อนุมัติโครงสร้างสารบัญคือใคร
2. จะเริ่มด้วยสารบัญภาษาไทยอย่างเดียว หรือเปิดป้ายกำกับไทย/อังกฤษตั้งแต่รุ่นแรก ทั้งนี้ไม่จำเป็นต้องแปลบทความทั้งหมด
3. ชุดคำค้น benchmark จะมาจาก analytics, support, คำถามผู้อ่าน หรือการรวบรวมโดยทีม และใครเป็นผู้ให้คะแนนความเกี่ยวข้อง
4. SLA ที่ยอมรับได้สำหรับการซิงก์แก้ไขและถอนเผยแพร่คือเท่าไร
5. มี shortlist สองตัวเลือกสำหรับ Thai bakeoff คือ Meilisearch และ Typesense; ตัวเลือกสุดท้ายยังรอผลทดสอบคำค้นจริง latency/ทรัพยากร ต้นทุน และการยืนยัน deploy/ดูแล โดยพิจารณาความสามารถ AI-native, hybrid retrieval และ reranker แต่ไม่บังคับให้เลือกตัวใดหากไม่ผ่านเกณฑ์
6. สถานะปัจจุบันของเอกสาร Typhoon v0.2.2 และซอร์สปลั๊กอินต้องตรวจสอบใหม่ก่อนกำหนดขอบเขตระยะที่ 2
7. ก่อนเริ่มพัฒนา production ต้องยืนยันงบประมาณ ผู้ดูแลระบบ และนโยบายสำรอง/กู้คืนร่วมกับผู้รับผิดชอบ WordPress

## ความสัมพันธ์กับระยะที่ 2

ระยะที่ 1 สร้างโครงสร้างที่แชตสามารถใช้ได้ในอนาคต ได้แก่รหัสถาวร แหล่ง URL ชัดเจน ข้อมูลรุ่น/แฮช การอ้างอิงระดับหัวข้อ ความสัมพันธ์ที่ผ่านการตรวจ และชุดส่งออกที่กรองเฉพาะเนื้อหาเผยแพร่แล้ว ระยะที่ 2 จึงค่อยประเมินและสร้าง Open Typhoon chat โดยใช้เฉพาะบทความที่ผู้ใช้มีสิทธิ์อ่าน ตอบพร้อมอ้างอิงไปยัง URL และ anchor จริง เคารพการถอนเผยแพร่ และไม่ให้ข้อความ prompt injection ในบทความเปลี่ยนคำสั่งระบบ เอกสาร Typhoon ที่ตรวจสอบระบุ API แบบ OpenAI-compatible สำหรับ Chat Completions; การเข้ากันได้ของ endpoint กับรุ่นที่ต้องการยังต้องทำ prototype และ API ดังกล่าวเพียงอย่างเดียวไม่ใช่ระบบค้นคืนหรือ index ของบทความ (ข้อสรุปหลังเป็นการอนุมานจากขอบเขต API ที่เอกสารอธิบาย)

ก่อนเริ่มระยะที่ 2 ให้ยืนยันสถานะปลั๊กอินและเอกสาร Typhoon ปัจจุบัน ตรวจซอร์สและสิทธิ์การเข้าถึง ทบทวนความปลอดภัย และทดสอบคำตอบกับชุดคำถามอ้างอิงโดยเฉพาะ

## ภาคผนวกทางเทคนิคและแหล่งอ้างอิง

### ผู้สมัครสำหรับ Thai bakeoff

- **Meilisearch:** เอกสารระบุการแบ่งคำไทยแบบพจนานุกรม และอธิบายการค้นแบบผสมระหว่างคำสำคัญกับความหมายผ่าน embedding; มีแนวทาง localized attributes สำหรับข้อมูลหลายภาษา [Language support](https://www.meilisearch.com/docs/resources/help/language), [hybrid search](https://www.meilisearch.com/docs/capabilities/hybrid_search/overview), [multilingual data](https://www.meilisearch.com/docs/capabilities/indexing/how_to/handle_multilingual_data)
- **Typesense:** เอกสารระบุ locale `th` และการแบ่งคำไทยโดยเฉพาะ; Search API มีทั้ง `query_by` สำหรับค้นข้อความและ `vector_query` สำหรับค้นเวกเตอร์ เอกสาร RAG จะใช้ประกอบการวางแผนระยะที่ 2 เท่านั้น ไม่ใช่เหตุผลให้บังคับเพิ่มแชตในระยะที่ 1 [Thai locale](https://typesense.org/docs/guide/locale.html), [Search API](https://typesense.org/docs/30.2/api/search.html), [Conversational Search/RAG](https://typesense.org/docs/30.2/api/conversational-search-rag.html)

เอกสารของแต่ละโครงการเป็นหลักฐานว่าความสามารถมีให้ทดสอบ ไม่ใช่ผล benchmark ของ HybridMind และไม่ยืนยันว่า reranker มีในตัว หากต้องใช้ reranker ให้รวมค่าระบบเพิ่มและ latency เข้า bakeoff

### WordPress และ Open Typhoon

- [WordPress Posts REST API](https://developer.wordpress.org/rest-api/reference/posts/) และ [hook `wp_after_insert_post`](https://developer.wordpress.org/reference/functions/wp_after_insert_post/): ใช้ตรวจรูปแบบการอ่านโพสต์ สถานะเผยแพร่ และจังหวะเริ่ม event ซิงก์
- [Open Typhoon API reference](https://docs.opentyphoon.ai/en/api-reference/): อธิบาย API แบบ OpenAI-compatible และ Chat Completions; ต้องทำ prototype เพื่อยืนยัน endpoint, รุ่นโมเดล และการเชื่อมกับ retrieval ก่อนระยะที่ 2
