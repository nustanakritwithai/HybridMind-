คำตอบโดยตรง: Claim Decomposition คือการแยกคำตอบยาวเป็นข้อกล่าวอ้างย่อยเพื่อให้ตรวจทีละข้อ แต่ต้องตรวจการแยกก่อนตรวจความจริง: แต่ละข้อยังตรงกับข้อความเดิมหรือไม่ เก็บเนื้อหาครบหรือไม่ และรักษาบุคคล รุ่น เงื่อนไขกับขอบเขตหรือไม่ จากนั้นจึงตรวจข้อย่อยกับแหล่งอ้างอิงแยกอีกชั้น ข้อที่มีหลักฐานรองรับภายนอกอาจเป็นข้อใหม่ที่คำตอบเดิมไม่เคยกล่าว ข้อที่แยกตรงต้นฉบับก็อาจยังไม่มีหลักฐานหรือขัดกับแหล่งข้อมูลได้

บทความมี Conceptual Architecture / HYPOTHESIS สำหรับผู้สร้าง Agent พร้อม Interactive และเกม SIMULATION สำรวจความต่างของการแยกกับการตรวจหลักฐาน ตัวจำลองใช้รายการข้อกล่าวอ้างที่ผู้เขียนกำหนด ไม่เรียก LLM, parser หรือ NLI และไม่สร้างผล benchmark ของ AI

ทำไมตัวตรวจความจริงต้องตรวจตัวแยกข้อความด้วย

สมมติคำตอบบอกว่า “Atlas Lab รุ่น2.1 อ่าน PDF ออฟไลน์ได้เฉพาะบนเดสก์ท็อป” ถ้าตัวแยกสร้างข้อย่อยว่า “อ่าน PDF ออฟไลน์ได้บนทุกอุปกรณ์” มันไม่ได้เพียงทำประโยคให้สั้นลง แต่เพิ่มขอบเขตที่คำตอบไม่ได้รับรอง ตัวตรวจปลายทางจึงกำลังตรวจข้อความอีกเรื่องหนึ่ง

อีกกรณีคือมีห้าข้อในคำตอบ แต่ตัวแยกส่งต่อเฉพาะสามข้อที่ตรวจแล้วว่ามีหลักฐาน คะแนนในกลุ่มที่เหลืออาจเต็ม แม้ข้อที่ยังไม่มีหลักฐานและข้อที่ขัดกับเอกสารถูกทำหาย การมีคะแนนสูงจึงอาจสะท้อนสิ่งที่ไม่ได้ถูกส่งไปตรวจด้วย

ให้ Agent เก็บต้นฉบับกับรายการข้อย่อยแยกกัน ไม่ใช้รายการที่ระบบสร้างแทนต้นฉบับแล้วถือว่าตรวจครบ ต้องดูสิ่งที่ไม่ได้ถูกส่งไปตรวจด้วย

บทความนี้เจาะคุณภาพตัวแยก ต่างจาก Retrieval Evaluation ที่ตรวจผลค้น/บริบท/คำตอบ และ Evidence Sufficiency ที่ตรวจว่าข้อเชื่อมพอสำหรับคำถามหรือไม่

Scientific Foundations: Atomic Claim เป็นหน่วยตรวจ ไม่ใช่ใบรับรองความจริง

FACT: งาน FActScore แยกข้อความเป็น atomic facts แล้วประเมินสัดส่วนที่แหล่งความรู้ที่กำหนดรองรับ โดยสูตรหลักคิดสัดส่วนต่อคำตอบและเฉลี่ยเหนือคำตอบที่ตอบจริง งานนี้ศึกษาชีวประวัติภาษาอังกฤษกับ Wikipedia จึงเป็นการตรวจ precision ตามแหล่งและเงื่อนไขของงาน ไม่ใช่ความครบหรือความจริงทั่วโลก FActScore, EMNLP 2023

งาน A Closer Look at Claim Decomposition แยกคุณภาพตัวแยกเป็น coverage, coherence และ atomicity และเสนอ DecompScore ที่ใช้ข้อความต้นฉบับเป็นแหล่งตรวจ สูตรดั้งเดิมเป็นจำนวนข้อย่อยที่ต้นฉบับรองรับโดยเฉลี่ยต่อ passage ไม่ใช่เปอร์เซ็นต์ความจริงจากเอกสารภายนอก การแยกผิดสามารถเปลี่ยนผลประเมินข้อความเดิมได้ DecompScore, *SEM 2024

Coverage ถามว่าเก็บสาระเดิมครบเพียงใด Coherence ถามว่าข้อที่แยกยังสอดคล้องกับสิ่งที่ต้นฉบับกล่าวหรือไม่ Atomicity ถามว่าแยกย่อยพอให้ระบุตำแหน่งปัญหาได้หรือยัง ทั้งสามไม่ได้แทนกัน รายการที่ตรงต้นฉบับแต่ขาดหลายข้อยัง coverage ต่ำ ส่วนประโยคที่รวมหลายข้ออาจตรงแต่ระบุข้อผิดพลาดรายส่วนได้ยาก

Atomic ต้องผูกกับเกณฑ์งาน “ออฟไลน์เฉพาะเดสก์ท็อป” ต้องรักษาเงื่อนไขกับความสามารถ การแยกคำเงื่อนไขลอย ๆ ไม่ได้ทำให้ตรวจดีขึ้น

ตรวจสองทิศ: คำตอบเดิมกับหลักฐานภายนอก

ชั้นแรกตรวจ Original Answer → Subclaim ถามว่าคำตอบเดิมกล่าวข้อย่อยนี้ด้วย entity รุ่น และเงื่อนไขใด การผ่านชั้นนี้หมายถึงแยกตรงในขอบเขตที่ตรวจ ไม่ได้หมายถึงเนื้อหานั้นจริง

ชั้นสองตรวจ Reference Source → Subclaim ถามว่าแหล่งที่กำหนดรองรับ ขัดแย้ง หรือยังไม่มีข้อมูลสำหรับข้อย่อยนั้น ต้องเก็บ reference IDs และช่วงข้อความที่ใช้ต่างจาก source spans ของคำตอบเดิม เพราะเป็นคนละต้นทาง

ตัวอย่างสมมติ C8 บอกว่า Atlas Lab รุ่น2.1 เปิด DOCX เมื่อออนไลน์ มี R5 รองรับ แต่ต้นฉบับไม่เคยกล่าวคุณสมบัตินี้ C8 จึงผ่านเรื่องหลักฐานภายนอกและไม่ผ่านเรื่องการแยก การเพิ่มข้อที่เอกสารรองรับก็ยังเป็นเนื้อหาใหม่

ในทางกลับกัน ข้อ “Nova Lab รุ่น1.4 แปลภาษาละตินได้” อยู่ในคำตอบเดิม แต่เอกสารสมมติไม่มีข้อมูลยืนยัน ควรเก็บข้อย่อยนี้พร้อมสถานะ NOT_IN_REFERENCE ไม่ลบให้คะแนนดูดี ส่วน “เก็บประวัติ30วัน” อยู่ในต้นฉบับแต่ขัดกับ R3 จึงต้องเก็บพร้อม CONTRADICTED การแก้ข้อความให้ตรงเอกสารเป็นขั้นแก้คำตอบอีกงานหนึ่ง

ตัวอย่าง Atlas Lab / Nova Lab: เก็บอะไรไว้บ้าง

ผลิตภัณฑ์ทั้งหมดต่อไปนี้เป็น SIMULATION คำตอบต้นฉบับมีห้าหน่วย U1–U5 และชุดเอกสาร R1–R5 ที่ผู้เขียนกำหนด ไม่ใช่ข้อเท็จจริงของซอฟต์แวร์ที่จำหน่ายจริง

source span คือช่วงของข้อความเดิมที่ข้อย่อยอ้างว่าแยกออกมา ให้เก็บข้อความช่วงนั้นพร้อม start/end และหน่วยตำแหน่ง ใน Lab ใช้ UTF-16 code units และ end แบบไม่รวมตำแหน่งสุดท้าย การมีตำแหน่งถูกยืนยันแค่การอ้างช่วง ไม่พิสูจน์ว่าการตีความช่วงนั้นถูก

Record ควรมี claim ID, original version, entity, predicate, qualifiers, spans และผลสองชั้น ห้ามผสม Atlas2.1กับNova1.4 การแก้สรรพนามต้องอิงต้นฉบับและคงความกำกวมเมื่อแก้ไม่ได้

Interactive: คะแนนสูงขึ้นเพราะเนื้อหาถูกทำหายหรือไม่

เริ่มจากข้อย่อย C1–C5 ที่รักษาห้าหน่วยเดิม ลองเปลี่ยนเป็นโหมดเลือกเฉพาะข้อที่เอกสารรองรับ C1–C3 แล้วดู Original Coverage แม้สัดส่วนที่เอกสารยืนยันจะเป็น3/3 แต่เนื้อหาคงเหลือเพียง3/5ของคำตอบเดิม ผลนี้ไม่ใช่การตรวจครบ

ลองโหมดเพิ่มข้อใหม่ C8 แล้วดูว่ามีหลักฐาน R5 แต่ไม่มี source span ในคำตอบเดิม หรือเลือก C7 ที่เปลี่ยน “เฉพาะเดสก์ท็อป” เป็น “ทุกอุปกรณ์” ส่วน C9/C10 แสดงการสลับผลิตภัณฑ์และเปลี่ยนรุ่น

      System Architecture: แยกหน้าที่ก่อนรวมคะแนน

      แผนต่อไปนี้เป็น Conceptual Architecture / HYPOTHESIS สำหรับ application ที่ตรวจคำตอบ Agent ไม่ใช่ implementation ที่งานวิจัยทั้งห้าใช้ร่วมกัน และยังต้องทดสอบการแยกภาษาไทยกับข้อมูลจริง

      ผังรวม ContextBinder กับ RedundancySelector เป็นหนึ่งกลุ่ม แต่ตารางแยกหน้าที่ชัด ควรเก็บข้อที่ถูกปฏิเสธหรือไม่แน่ชัดไว้ใน audit record พร้อมเหตุ ไม่ลบทิ้งจนตรวจย้อนหลังไม่ได้

      Report + Memory ต้องเก็บข้อเดิมพร้อมสถานะและ provenance ใน audit record การรักษาข้อที่ขัดแหล่งหรือยังไม่ยืนยันไม่ได้อนุญาตให้เผยแพร่หรือใช้เป็น trusted fact รอบถัดไป การแก้ไข/อนุมัติต้องเป็น revisionและสถานะที่ตรวจใหม่

      Ledger เป็น External Memory ข้อมูลที่นำมาอ่านเป็น Retrieved Context ใน Context Window การเขียนไฟล์/เปลี่ยนpromptไม่อัปเดต Model Weights การฝึกevaluatorต้องระบุtraining dataและประเมินแยก

      Operational Flow: ตรวจต้นฉบับก่อนตรวจเอกสาร

      ขั้นแรก เก็บคำตอบต้นฉบับและขอบเขตงาน เช่นต้องแยกทุก assertion หรือเฉพาะข้อที่ตรวจสอบได้ อย่าใช้เอกสารภายนอกเขียนต้นฉบับใหม่ก่อน audit เพราะจะไม่เห็นข้อที่โมเดลกล่าวเกิน

      ขั้นสอง สร้าง candidate พร้อม source spans และเก็บ entity/version/qualifiers ถ้าระบุต้นทางไม่ได้ให้ส่ง ambiguous หรือ introduced เพื่อทบทวน การมี JSON fields ครบไม่รับรองว่าค่าใน fields รักษาความหมาย

      ขั้นสาม ตรวจทั้งข้อที่เพิ่มและข้อที่หาย ต้องดู original→candidate และ original coverage ด้วย ผล audit ไม่ควรตัดสินความจริง ถ้าคำตอบเดิมมีข้อผิด ให้เก็บข้อผิดนั้นตรง ๆ เพื่อส่งไปตรวจ

      ขั้นสี่ เติมบริบทโดยแยก target กับ background พร้อม provenance ถ้า target/entity/qualifiersเปลี่ยนให้ตรวจเทียบต้นฉบับใหม่ บริบทจากแหล่งอื่นต้องมีtag ไม่ถูกนับเป็นข้อเดิมโดยเงียบ ๆ จากนั้นคัดข้อซ้ำพร้อมเก็บraw/rejectionlogและคำนวณ originalcoverageหลังคัดใหม่

      ขั้นห้า ตรวจ target กับแหล่งที่ระบุ รวมรุ่น วันที่และ evidence spans แยก SUPPORTED, CONTRADICTED และยังไม่มีข้อมูล อย่าอ้างความจริงสากลจากผลเทียบชุดเอกสารที่จำกัด

        Limitations / Failure Modes
        




        Qualifier หาย: คำว่าเฉพาะ เมื่อ หรือรุ่นใดจำกัดข้อกล่าวอ้าง การตัดออกอาจขยายขอบเขต ต้องเก็บความสัมพันธ์ ไม่เก็บคำเงื่อนไขเป็นข้อความลอย ๆ
        




        Reference ปะปนกับต้นฉบับ: ข้อมูลจากเอกสารที่ถูกเติมเข้า extraction อาจจริงตามแหล่งแต่ไม่ได้กล่าวในคำตอบ ให้ตรวจ provenance ของ record และแยกการแก้เนื้อหา
        




        ข้อมูลซ้ำกับตัวหาร: การนับ paraphraseเป็นหลายหน่วยหรือทิ้งข้อยากทำให้ supportratioเปลี่ยนโดยสาระไม่ดีขึ้น เก็บ raw/normalized counts และ coverageคู่กัน
        




        Span ถูกแต่ตีความผิด: การอ้าง offsetsและquoteไม่ได้รับรอง entitybindingหรือentailment และoffsetต่างระบบอาจเป็นbytes/codepoints/UTF-16 ต้องระบุหน่วยกับเวอร์ชัน
        




        ผู้ตรวจ semantic ผิด: ทั้ง extractor และ verifier มี error model ข้อมูลภาษาไทย/โดเมนใหม่ยังต้องตรวจ ไม่อนุมานผลทุกภาษาจากการทดลองภาษาอังกฤษ
        




        เอกสารไม่ครบหรือผิด: NOT_IN_REFERENCE ไม่แปลว่าfalse และ SUPPORTED ไม่แปลว่าพิสูจน์โลกจริง ต้องรายงานขอบเขตแหล่งรวมความขัดแย้งที่พบ
        




        Future Directions และ Practical Takeaways
        




        ควรทดสอบ audit ข้อเพิ่ม/ขาดพร้อม uncertainty การรักษา entity/qualifiers และการตรวจใหม่เมื่อต้นทางเปลี่ยน ข้อเสนอเป็น HYPOTHESIS ยังไม่พิสูจน์ผลกับ Agentจริง
        








        เก็บoriginal/span mapping ดูการรักษา ความครบ atomicityและหลักฐานแยกกัน เก็บrejectionlogและcoverageหลังคัด คะแนนเดียวไม่รับรองว่าข้อเพิ่ม/ตกหล่นดีขึ้น
        




        หลักใช้งานคือ แยกให้ตรงก่อนตรวจให้จริง เก็บแม้ข้อที่ยังไม่มีหลักฐานหรือขัดแหล่งเพื่อประเมินต้นฉบับตามจริง แล้วจึงสร้างคำตอบ revisionที่แก้ไขอย่างมีบันทึก อย่าใช้การแยกเป็นช่องทางเขียนเนื้อหาใหม่โดยไม่มีร่องรอย
